# Linux adapter: best effort

Linux support is agent-routed rather than a first-class step-by-step path. Read the [manifest](https://starter.devthomas.site/setup/computer-setup.manifest.json), inspect distribution, architecture, shell, package manager, harness support, and prior state. Resolve current vendor instructions for that distribution before proposing changes.

Apply the same inspect, batch approval, install, verify, and resume sequence as [Computer Setup](https://starter.devthomas.site/skills/computer-setup/current/SKILL.md). Use supported native package sources and verify executable discovery and capability. Preserve working tools and avoid downgrades. Record unsupported capabilities honestly rather than claiming platform parity.

Begin with existing local or portable progress; a GitHub repository is not an entry prerequisite. Prioritize Git and GitHub CLI after their prerequisites, then guide sign-in. As soon as GitHub write access works, follow the [progress guide](https://starter.devthomas.site/artifacts/progress/README.md) to create or confirm a private repository, save progress, and verify the remote files. An already-working connector can save progress sooner. Preserve checkpoints through interruptions; a failed remote save blocks Quick Build, not independent setup work.

Follow [remote access](https://starter.devthomas.site/setup/remote-access.md), selecting an interaction layer that supports the machine and phone. Save the latest nonsecret progress and setup results to the private repository and verify the remote revision. Setup is complete only when capability checks, phone interaction, and this remote save have succeeded.
