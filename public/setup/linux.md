# Linux adapter: best effort

Linux support is agent-routed rather than a first-class step-by-step path. Read the [manifest](https://starter.devthomas.site/setup/computer-setup.manifest.json), inspect distribution, architecture, shell, package manager, harness support, and prior state. Resolve current vendor instructions for that distribution before proposing changes.

Follow the [IDE setup guide](https://starter.devthomas.site/setup/ide.md) in the required installation batch: Antigravity IDE for Antigravity, Cursor for Cursor, and VS Code for all other development harnesses, including ChatGPT/Codex and Claude Code. The agent installs and configures the selected IDE for the distribution and architecture, preserves working settings, and verifies launch, workspace access, the integrated terminal and Git. Record the `selected-ide` result; CLI-only or cloud-only access does not substitute for the selected desktop IDE.

At setup start, follow the [Workbench lifecycle](https://starter.devthomas.site/artifacts/progress-workbench/README.md) to place the generic `index.html` beside canonical `starter-progress.json`, preserving existing HTML and progress. Ask for missing development account and notification email choices once, using the [progress guide](https://starter.devthomas.site/artifacts/progress/README.md); record only confirmed choices and do not change Git identity. The local viewer starts independently of GitHub and never gates setup.

As soon as Python is verified, invoke its resolved interpreter with `-m http.server PORT --bind 127.0.0.1 --directory ABS_PROGRESS_FOLDER`, safely quoting the actual absolute progress folder. Inspect an existing listener and reuse it only if its directory and loopback binding match; otherwise select the first free port from 8000 through 8010. Follow the lifecycle for background launch, verification, process records, and resume. Do not stop unrelated servers, expose a broader workspace, or bind to the LAN. Refresh after progress writes; the visible HTTP view also polls every five seconds, while file mode requires choosing the saved JSON again. A viewer failure is a follow-up rather than a setup blocker.

Apply the same inspect, batch approval, install, verify, and resume sequence as [Computer Setup](https://starter.devthomas.site/skills/computer-setup/current/SKILL.md). Reuse healthy installations. Compare supported native package sources and vendor binaries for missing capabilities, including provenance, architecture, dependencies and update/repair paths. No named package manager is a gate when approved direct tools suffice. Python remains required up front; use uv to discover a healthy interpreter or provision a supported one. Avoid unnecessary source builds, conflicting installers and downgrades. Record unsupported capabilities honestly rather than claiming platform parity.

Follow the [cross-context checks](https://starter.devthomas.site/setup/tool-troubleshooting.md#command-resolution-in-each-context) in the current shell, a fresh terminal, the IDE integrated terminal and the actual harness subprocess. Test alternate shells only when selected, preserve profiles, and verify ordinary command resolution after persistent changes. A shell pass is not a harness pass. Keep project-local tools in their repository runner, not globally accumulated `node_modules/.bin` paths. Record per-tool source, scope, path, version, architecture, time and context outcomes in the existing setup state without a full environment dump.

Begin with existing local or portable progress; a GitHub repository is not an entry prerequisite. Prioritize Git and GitHub CLI after their prerequisites, then follow [provider authentication and Git privacy](https://starter.devthomas.site/setup/authentication.md) before the first useful push. As soon as GitHub write access works, follow the [progress guide](https://starter.devthomas.site/artifacts/progress/README.md) to create or confirm a private repository, save progress, and verify the remote files, revision and private visibility. An already-working connector can save progress sooner. Preserve checkpoints through interruptions; a failed remote save blocks Quick Build, not independent setup work.

Follow [remote access](https://starter.devthomas.site/setup/remote-access.md), selecting an interaction layer that supports the machine and phone. Confirm both Tailscale clients and device identity, [file receipt in both directions](https://starter.devthomas.site/setup/file-transfer.md), and a phone action in the actual harness separately. Save the latest nonsecret progress and setup results to the private repository and verify the remote revision. Reconcile against the canonical requirements rather than using a combined legacy remote flag. Optional [private Workbench access](https://starter.devthomas.site/setup/private-workbench.md) requires separate approval and an isolated snapshot, never proxying the private-repository listener. Neither the viewer nor email preferences gate setup. Use [conditional troubleshooting](https://starter.devthomas.site/setup/tool-troubleshooting.md) for later selected tools; do not imply all Linux distributions or physical-phone routes were tested.
