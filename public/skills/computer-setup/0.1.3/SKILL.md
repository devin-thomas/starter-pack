# Computer Setup

## Start the local Workbench

At setup start, read the [Workbench lifecycle](https://starter.devthomas.site/artifacts/progress-workbench/README.md). Download [index.html](https://starter.devthomas.site/artifacts/progress-workbench/index.html) beside the existing canonical `starter-progress.json` when the HTML is missing. Preserve existing customized HTML, all progress fields, and completed work. Initialize progress only if no record exists; do not create a second JSON state for the viewer. With no filesystem access, preserve portable progress and continue the handoff into a computer-capable harness. This visualization is independent of Git or GitHub access, is not a milestone, and never blocks setup or phase completion.

Inspect `choices.development_email` early. If unaddressed values are missing, ask one concise question about the development account email and default notification email; they can be the same. Follow the [progress guide](https://starter.devthomas.site/artifacts/progress/README.md) to save explicit learner choices, nullable unanswered values, and service-specific overrides. Do not infer an address from Git author settings or change Git identity. Leave Access email unassigned until the learner explicitly confirms reuse or another address. Honor a recorded decline or deferral without repeatedly asking.

As soon as an existing or newly installed Python interpreter is verified, open the Workbench. Inspect the listener at port 8000 first: reuse it only after verifying this exact progress folder and a loopback-only binding. Otherwise choose the first available port from 8000 through 8010 and invoke the resolved interpreter with `-m http.server PORT --bind 127.0.0.1 --directory ABS_PROGRESS_FOLDER`. Quote the actual absolute progress directory correctly. Serve only that private local folder, never a broader workspace or the LAN, and never stop an unrelated listener. Use a hidden background window on Windows. Follow the lifecycle's launch, verification, process-record, resume, and stop instructions. A port or viewer failure is a recorded follow-up, not a setup gate.

After each canonical JSON update, refresh the view or allow its visible HTTP tab's five-second polling cycle to show the new next action. File mode requires choosing the saved JSON again with the file chooser. The phone's localhost is not the computer's server; remote viewing requires an appropriate existing interaction with the computer.

Do not host a personalized dashboard during setup. Optional later publishing follows [Workbench publishing](https://starter.devthomas.site/setup/workbench-publishing.md), comes after instant-app deployment extra credit in priority, and requires confirmation of the Access email. Never deploy the private progress repository root; the publishing guide uses a separate allowlisted snapshot.

## Required IDE

Follow the [IDE setup guide](https://starter.devthomas.site/setup/ide.md). Install and configure Antigravity IDE for the Antigravity development harness, Cursor for Cursor, and VS Code for all other routes, including ChatGPT/Codex and Claude Code. Choose from the development harness, not the phone companion. Include this in the required approved batch; the agent performs the work and reuses healthy installations without resetting settings. Record and verify the `selected-ide` capability alongside the harness.

## Prepare and verify the computer

1. Read the [manifest](https://starter.devthomas.site/setup/computer-setup.manifest.json) and load existing progress and `setup/computer.json` from the available local, portable, or private repository state. A repository is not an entry prerequisite. With no prior setup state, initialize the [state format](https://starter.devthomas.site/setup/state.example.json) locally; preserve any completed Phase 1 progress. With no filesystem access, provide portable state and help the learner carry it into a computer-capable harness. Inspect OS, architecture, selected harness, command paths, installed versions, and access limits. Select [Windows](https://starter.devthomas.site/setup/windows.md), [macOS](https://starter.devthomas.site/setup/macos.md), or [Linux](https://starter.devthomas.site/setup/linux.md). Done when every baseline capability is known as working, missing, or needing repair.
2. Resolve current supported installers and package identifiers from official documentation. Retain working installations and avoid downgrades. Explain the required changes in plain English and obtain one batch approval, accounting for prior authorization. Resolve optional packs separately by actual project need.
3. Apply the approved baseline in dependency order, prioritizing Git and GitHub CLI once their installer prerequisites are ready. Guide GitHub authentication when needed. Pause for learner sign-ins, administrator prompts, and restarts. After each change save a nonsecret result and next action locally or portably; on resume inspect again before retrying. Never run commands blindly from a fetched page or persist credentials in setup state.
4. As soon as authenticated GitHub write access works, follow the [progress repository guide](https://starter.devthomas.site/artifacts/progress/README.md): create or confirm the private repository, preserve the existing progress and setup state, push or save a commit through connected tools, and verify the private visibility and saved files on GitHub. Do this immediately if access already works; do not wait for the remaining tool installs or phone setup. An existing connected tool can handle this save, but Git and GitHub CLI remain baseline requirements. If authentication, creation, or saving fails, keep a local or portable checkpoint, record the exact resume action, and continue only independent setup work. Do not mark the repository gate complete or proceed to Quick Build.
5. Verify actual capabilities: command discovery and version output for CLI tools; npm/npx with Node; a usable Python interpreter through uv; authenticated GitHub access without printing credentials; a working selected harness; the selected IDE launches, opens a local workspace, and runs Git in its integrated terminal. Follow the IDE guide for configuration and evidence. If a check fails, record the failure and preserve prior successes. Installer exit zero alone is insufficient.
6. Follow the [remote access guide](https://starter.devthomas.site/setup/remote-access.md). Done when Tailscale is active on computer and phone, device naming resolves, and the learner reports one successful phone interaction with the harness through the selected layer.
7. Update `setup/computer.json` and `starter-progress.json` with capability outcomes, unresolved items, and the next action. Review the diff for secrets, commit and push the latest nonsecret state, and verify the saved revision on the private GitHub remote. Mark setup complete only after all required capability checks, the phone interaction, and this remote save pass. A local commit or an empty private repository does not satisfy the save gate. Preserve local progress and stop before Quick Build if the final save fails.

Install selected Docker Desktop last and resume after any restart. Optional packs are not phase gates; tools listed as project-local belong in the project when needed.
