# Build Something Serious

This phase is a preview in this release. The complete guided curriculum is not available yet. You can still use these questions to prepare a serious project with your agent.

<h2 id="featured-perfect-playlist">Perfect Playlist</h2>

I made Perfect Playlist to carry an exact music selection into Spotify, preserving the chosen tracks, their order, and intentional repeats. Its website introduces the tool and agent onboarding. The lessons here show how I made its operations and verification explicit.

## Choose the idea you want to grow

Start with the person you want to help and the problem they encounter. Describe the smallest useful version, why someone would return to it, and the boundaries that keep the first release achievable. A second small harness build is optional if you want more practice first.

<section class="field-lesson" aria-labelledby="phase-3-keep-the-choice">

<p class="eyebrow">From my projects · Perfect Playlist</p>

<h3 id="phase-3-keep-the-choice">Keep the choice you already made</h3>

I wanted the exact Spotify playlist I had chosen. An agent could help explore music and make selections, but the final handoff needed to preserve that decision. Perfect Playlist separates finding possibilities from writing the playlist: Search finds candidates, Inspect reveals facts, and Build or Add receives the exact choices.

That separation matters when order is part of the experience. A repeated track can also be intentional. The core representation, called a TrackSequence, keeps exact track references in order and preserves duplicates. A song title alone cannot reliably identify a particular recording.

</section>

<section class="field-lesson" aria-labelledby="phase-3-find-the-handoff">

<p class="eyebrow">Try it in your project</p>

<h3 id="phase-3-find-the-handoff">Find the handoff from choice to action</h3>

For your idea, look for the point where exploration should end and an exact action should begin. A tool handling an approved publishing queue or an ordered set of files could use the same approach. Those are possible adaptations: the lesson is to preserve the decision, including details that a helpful-sounding rewrite might lose.

> Ask your agent: "Where does this workflow need judgment, and where must it follow an exact choice? Define what identity, order, and duplicates mean before we implement the action."

</section>

## Make decisions visible

Ask your agent for a full grill-to-build conversation: work through product assumptions, constraints, risks, and unresolved choices before committing to implementation. Unlike Quick Build's short interview, this may take several rounds. Have the agent maintain the specification, decision records, project context, ordered tasks, and project instructions so another session can follow them. Review its summary and correct anything that does not match your intent.

A skill is a focused set of instructions an agent can load for a particular kind of work. Ask which skills your project needs, when it will use each one, and what each skill is allowed to change. Have the agent show you the instructions and explain unfamiliar terms before granting new tools access to your project.

<section class="field-lesson" aria-labelledby="phase-3-package-the-operation">

<p class="eyebrow">From my projects · Perfect Playlist</p>

<h3 id="phase-3-package-the-operation">Give the next session a reliable operation</h3>

I packaged Perfect Playlist as a command-line tool and an importable Python package, with a hosted skill to explain its use to agents. Different ways of using the project could share the same operation instead of rebuilding the behavior in every conversation.

Its language gives that operation boundaries. A Source supplies supported input. A TrackSequence represents the selected tracks. Build and Add perform different changes; Verify checks the result. Naming those responsibilities helps a person or another agent understand what is about to happen.

</section>

<section class="field-lesson" aria-labelledby="phase-3-describe-one-operation">

<p class="eyebrow">Try it in your project</p>

<h3 id="phase-3-describe-one-operation">Describe one operation completely</h3>

You can practice this before writing a reusable package. Have your agent describe one operation's inputs, intended changes, output, and failure behavior. Check that its instructions only promise behavior the tool supports. A skill can explain a tool; loading that skill does not itself authorize changes to someone's external account.

> Ask your agent: "Write the instructions another session would need to use this operation correctly. Include when it must stop and what permission it needs."

</section>

## Add complexity for a reason

Persistent data may justify a database. Individual user spaces may justify authentication. Selling something may justify payments. External information may justify APIs or integrations. Each creates operating responsibilities, so introduce it when your product actually needs it. Discuss data ownership, access, recovery, costs, review, and proportionate testing alongside the feature.

<section class="field-lesson" aria-labelledby="phase-3-check-the-outcome">

<p class="eyebrow">From my projects · Perfect Playlist</p>

<h3 id="phase-3-check-the-outcome">Check what the service actually saved</h3>

In my project's July 18, 2026 testing record, a request to create a private playlist was acknowledged, but reading the result back reported a public playlist. The tool stopped before adding tracks. The documented private-build path used an already-private, owned empty playlist instead. This is a historical observation from that project, not a current test of Spotify's behavior.

</section>

<section class="field-lesson" aria-labelledby="phase-3-define-proof-of-success">

<p class="eyebrow">Try it in your project</p>

<h3 id="phase-3-define-proof-of-success">Define the proof of a successful change</h3>

The lesson reaches beyond playlists. A successful response is one piece of evidence. The intended outcome also includes the right target, contents, and access settings. Read those back when they matter. Verification can reveal a mismatch, but it does not automatically undo a change or make a retry safe.

For an integration in your serious project, define the exact authorized change and the evidence that would confirm it. Discuss partial failures before adding automatic retries. Keep offline checks separate from tests that actually write to an external account.

> Ask your agent: "How will we confirm the intended state after this change? What happens if only part of it succeeds, or the result has the wrong access settings?"

</section>

The intended milestone is being able to structure and begin a serious project deliberately. This preview does not award a completion badge or claim to teach every operating decision. Bring your idea and the lessons from [your meaningful build](/phases/2) to your agent, and decide the next bounded step together.
