# Make It Agent Native

You have built software. Now choose one useful thing an AI agent should be able to find, read, or do with it, and give your project a real interface for that. This phase is about a better interface, not a bigger app. It is optional, and you decide how far to go.

This phase is a preview. You can choose a project and a level with your agent now. The step-by-step guide for each level is still being tested, so your agent tells you which parts are ready before you start.

<h2 id="featured-perfect-playlist">Perfect Playlist started with a Tiny Desk</h2>

After watching [The Paradox's Tiny Desk concert](https://www.youtube.com/watch?v=nkG2SSzPUns), I asked my agent to make a playlist of the exact songs. The setlist was public. It seemed like a simple request, but the agent repeatedly got it wrong.

I got stubborn. I could have assembled the playlist myself, but I wanted to ask and receive. Perfect Playlist grew out of that insistence: take a Tiny Desk setlist, verify the songs, and turn that selection into a playlist, with Spotify as an optional destination.

I care about carrying the feeling of a performance into what I listen to next. I believe other music lovers want that too. Finding those people is part of the work ahead.

## Choose your project

After you finish Phase 2, your agent offers this phase. Nothing starts until you choose it. Then pick what to work on:

- **Extend your Phase 2 build.** Give the project you just made a way for agents to use it.
- **Another project you already have.** Any existing project you can change and test counts.
- **A new project.** Start something small when a fresh idea fits the interface better.

Your agent reads the project's actual source and notes before proposing changes. It reuses the repository and decisions you already have, and it keeps your Phase 1 and Phase 2 records as they are. If you have not finished Phase 2, continue there first; reading this page does not mark Phase 2 complete.

## Choose what an agent should do

Tell your agent what an agent should find, read, or do with your project. It recommends the level that fits what you built and what you want, and you can choose any other level instead. You never need all four, and none of them asks you to make the app bigger or add accounts, payments, a database, a domain or a paid service.

### Level 1: Discoverable

For a public website. Make your approved public content easy for an agent to find and read: clear page structure, and a truthful `llms.txt` or focused readable pages where they help. Check it by asking a separate agent a question about your site. It should answer from your page, link to it, and decline anything you have not published. Level 1 earns a readiness milestone. It does not finish Phase 3 on its own.

### Level 2: Operable

Give your project one useful operation an agent can run. Choose the lane that fits: a command-line tool (CLI) for software that runs on a computer, or an HTTP API for a web app or hosted tool. Either lane is enough, and a read-only operation is a good start. The command or endpoint should be documented, return structured output such as JSON, and fail visibly with a clear error.

### Level 3: Connected

Connect your assistant to a tool you built using MCP (the Model Context Protocol). First connect a known-good example server and call one of its tools, so you know your assistant supports it. Then give your own project one safe MCP tool or resource, starting read-only. Connecting a tool to your assistant does not publish a plugin anywhere.

### Level 4: Full Agent Native

For larger projects that need the same capability in more than one place. Describe the capability once with the released Uppercut Agent Native package, `@uppercut-labs/agent-native`, and offer it as the command, API or MCP tool you need. Installing the package is not the finish line; a working command, API or MCP tool is.

## Prove it with a real client

Phase 3 is complete when one command, API or MCP tool (from Level 2, Level 3, or built through Level 4) passes all four checks:

1. A real agent or client you use invokes it. A simulation or a description of the call does not count.
2. The output is checked against what you expected.
3. One deliberate failure, such as a wrong input or a denied request, is checked too.
4. You confirm the result.

A Level 1 readiness milestone is recorded on its own. Levels you skip, save for later, or that do not fit your project never block completion.

## Save your milestones

Your agent records your project choice and each level in the same private progress file you have used since Phase 1. It saves only short notes: which client ran the check, which operation it called, and whether each check passed. It never saves passwords, keys, tokens, private data or logs there. You do not need a new account or another repository. Your Progress Workbench shows each level and whether Phase 3 is complete.

## Plan the smallest agent-facing change

Plan the interface with your agent using Grill to Build: what the agent should do, what goes in and comes out, which permissions it needs, how you will know it worked, and the failure you will test. Keep the plan short and review it before implementation. Use focused skills to carry the work between sessions.

Add only the engineering skills the project needs, including appropriate dated recommendations from Matt Pocock's resources when useful. Have the agent verify native discovery rather than calling a copied Markdown file an installation. A full 25-skill bundle is not required. Review, TDD, and orchestration can be introduced when relevant; Sandcastle or other AFK execution remains optional advanced work with a meaningful plan, bounded permissions, isolation, and cost/failure controls. Docker and Rosetta remain conditional, not graduation requirements.

<h3 id="phase-3-plan-the-pipeline">Give each stage a clear job</h3>

The agent researches the public setlist and reviews the song matches. The tool receives the selected tracks, preserves their order, and handles the requested output. That became a buildable sequence: discovery, selection, playlist creation or export, and a check of the result.

</section>

## Set up the integration deliberately

An API lets your project work with another service. Plan the developer account, registered application, permissions, and authentication it needs. Keep credentials outside the repository. Build and test the smallest complete connection before adding more services.

<section class="field-lesson" aria-labelledby="phase-3-connect-spotify">

<h3 id="phase-3-connect-spotify">Connect Spotify through a developer app</h3>

Perfect Playlist's Spotify path uses a registered developer app and OAuth, which lets someone authorize access to their account. Setup includes a callback address for returning from sign-in. The implementation separates finding tracks from writing the approved playlist, so each part can be tested on its own.

</section>

## Release something another person can install

A release includes packaging, a version, installation instructions, and a working example. Have your agent check installation outside the development environment and document the setup a new user needs.

<h3 id="phase-3-release-on-pypi">Publish the package and its agent instructions</h3>

I released [Perfect Playlist on PyPI](https://pypi.org/project/perfect-playlist/), Python's package index, so people can install it on their own computers. It includes a command-line tool and an importable Python package. A hosted skill gives agents the instructions to use it.

</section>

## Give the release a home

I bought **perfectplaylist.dev**, connected the domain to the hosted site, and added the project to [my portfolio](https://devthomas.site/). That gives potential users a place to start and employers a concrete piece of my work to inspect.

For your release, choose a domain if it serves the project, connect its DNS records to your host, and check HTTPS. Publish a clear description, screenshots, installation or usage instructions, and a source link. Then link it from your portfolio with the problem you solved, your technical decisions, and what you shipped.

**A portfolio can also be the project you grow here.** My certification tracker at [devthomas.site](https://devthomas.site/) became a home for work like Perfect Playlist. You could take a small Phase 2 portfolio further with a repeatable way to publish updates, a custom domain, and project case studies that show employers how you build.

The next step is finding listeners who share the original need. The Tiny Desk story gives me a specific way to introduce Perfect Playlist and learn who wants it.

Bring the lessons from [your meaningful build](/phases/2) into this phase. Phase 3 is complete when one capability passes the real-client checks above, not when a plan, a domain or a package exists.
